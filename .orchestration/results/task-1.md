## Decisions and deviations

1. **`AppLogger.subsystem` is a public (internal) static constant**, matching MacDictate's
   `AppLogger` exactly. §5.1 lists only the five `Logger` properties; the extra `subsystem`
   constant is how MacDictate expresses the same thing and is what the test asserts against.
   It is additive, not a contract change.
2. **`AppDelegate` constructs `AppCoordinator` inside `applicationDidFinishLaunching`, after
   the `XCTestCase` guard**, rather than in `init()` as MacDictate does. The task prompt
   requires the guard to run "before constructing/starting" the coordinator, so the
   coordinator is a `private var coordinator: AppCoordinator?`. Under a test run it is never
   constructed at all.
3. **`applicationWillTerminate` calls `coordinator?.stop()`.** This is the only caller of the
   pinned `stop()`; without it `stop()` would be dead code in the shell.
4. **No `.commands { }` block on the `Settings` scene.** MacDictate has one only to reroute
   ⌘, to its real settings window; MacPict has no settings window (plan §8), so that block
   would be dead weight.
5. **`.gitignore`** is MacDictate's list minus its `*.wav` entry. `DerivedData/`, `.DS_Store`,
   `build/`, `*.xcuserstate`, `xcuserdata/` are all present. Neither `.orchestration/` nor
   `MacPict.xcodeproj/` is ignored.
6. **`AppLoggerTests.testEachLoggerUsesItsOwnCategory`** verifies the pinned categories by
   comparing `String(reflecting:)` of each logger against an independently constructed
   `Logger(subsystem: AppLogger.subsystem, category: <expected>)`. `Logger` exposes neither
   its subsystem nor its category, but `os_log` caches one log object per
   (subsystem, category) pair — verified empirically before writing the test: identical
   pairs reflect equal, differing categories reflect unequal. This is the only way found to
   actually assert the category contract rather than merely assert that a `Logger` exists.
   Risk: it relies on that caching being stable; if a future OS drops the cache, the test
   fails loudly rather than silently passing. The suite also asserts the subsystem equals
   `Bundle.main.bundleIdentifier` and `"com.macpict.app"`, that all five identities are
   distinct, and that every logger is live (`isEnabled(type: .fault)`).

### Can ⌘, actually reach an accessory app?

I did **not** verify this at runtime — the instruction was not to launch the app, so this is
reasoning plus static evidence, not an observation. My reading is that it does reach the
user, and I did not find grounds to stop:

- `LSUIElement`/`.accessory` suppresses *display* of the menu bar; it does not suppress
  `NSApp.mainMenu` itself. `NSApplication.sendEvent(_:)` offers a key-down to
  `mainMenu.performKeyEquivalent(_:)` before the responder chain, and that path does not
  depend on the menu bar being drawn.
- Evidence that the mechanism is live in this app: the shell's own status-item menu already
  carries `keyEquivalent: "q"` on Quit, and MacDictate — also `LSUIElement` — ships this exact
  `CommandGroup(replacing: .appSettings)` construction for the same purpose.
- The caveat in the instruction holds and I am not claiming otherwise: this only fires while
  MacPict is the active app with one of its own windows key (the annotation window, or the
  settings window once open). With another app frontmost, `⌘,` belongs to that app — the
  global hotkey and the status-item menu remain the only entry points then.

So the change is not a no-op, but its reach is narrower than `⌘,` in a regular app. Worth a
manual check on your relaunch: open the annotation window, press `⌘,`, confirm settings
appears.
